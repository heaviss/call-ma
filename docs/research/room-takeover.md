# Можно ли войти в чужую комнату или подменить собеседника

Ресерч к [#48](https://github.com/heaviss/call-ma/issues/48), карта [#39](https://github.com/heaviss/call-ma/issues/39). Версии: call-ma на `87ae150`, Trystero `@trystero-p2p/*` 0.26.0. Ссылки на Trystero ведут в `node_modules/@trystero-p2p/*/dist` (собранный код пакета) и в его `README.md`.

## Коротко

- ID комнаты: 8 символов `[a-z0-9]` из `Math.random()`. Это 36⁸ ≈ 2,8·10¹² вариантов, около 41 бита.
- Релеи видят не ID, а его SHA-1. По этому хешу ID восстанавливается офлайн-перебором: от минуты на одной видеокарте до нескольких дней на ноутбуке.
- Trystero шифрует SDP ключом, который зависит только от `appId` и ID комнаты. Пароль мы не передаём. Кто знает или подобрал ID, тот читает и подделывает сигнализацию.
- Третий, вошедший в комнату, **молча получает камеру и микрофон обоих**: адаптер отдаёт локальный поток каждому новому пиру, а лимита на двух участников нет.
- Ссылка Direct mode несёт SDP открытым текстом: deflate и base64url, без шифрования. Перехвативший видит IP и может подсунуть свой ответ, но медиа не расшифрует.

## 1. Как устроен ID комнаты

`generateRoomId` в `src/app/controller.ts:22-25`:

```ts
const chars = 'abcdefghijklmnopqrstuvwxyz0123456789';
return Array.from({ length: 8 }, () => chars[Math.floor(Math.random() * chars.length)]).join('');
```

- Алфавит 36 символов, длина 8: 36⁸ = 2 821 109 907 456 ≈ 2^41,36.
- `getRoomIdFromUrl` принимает только `^[a-z0-9]{8}$` (`src/shared/link.ts:1`), так что пространство ровно такое.
- Источник случайности `Math.random()` — не CSPRNG. Самостоятельной атакой это не считаю: чтобы восстановить состояние генератора V8, нужны его выходы из той же вкладки. Но фикс стоит одной строки: `crypto.getRandomValues`.
- ID лежит во фрагменте URL (`#…`), а браузер не отправляет фрагмент серверу (RFC 3986 §3.5). GitHub Pages ID не видит. Видят все, через кого прошла ссылка: мессенджер, история чата, скриншот.
- Комната живёт, пока открыта вкладка. Trystero переанонсирует её раз в 60 с (`defaultSteadyAnnounceIntervalMs = 6e4`, `core/dist/topic-strategy.mjs:5`). Срока жизни у ссылки нет: старая ссылка из чата работает, пока у кого-то открыт звонок.

## 2. Что получают релеи

### Топик

`core/dist/strategy.mjs:39-43`:

```js
const rootTopicPlaintext = topicPath(libName, appId, roomId); // "Trystero@call-ma@<roomId>"
const rootTopicP = sha1(rootTopicPlaintext);
const selfTopicP = sha1(topicPath(rootTopicPlaintext, selfId));
const key = genKey(config.password ?? '', appId, roomId);
```

`appId` у нас константа `'call-ma'` (`src/connection/trysteroAdapter.ts:53`). Строка `Trystero` берётся из `libName` (`core/dist/utils.mjs:3`). `sha1` склеивает байты SHA-1 в base36 (`core/dist/crypto.mjs:11`).

Что видит каждый Transport:

| Transport                                          | Что уходит на релей                                                                                  | Источник                           |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------- |
| MQTT (`broker.emqx.io`, `broker.hivemq.com` и др.) | имя MQTT-топика = SHA-1-топик, тело = JSON с зашифрованным SDP                                       | `mqtt/dist/index.mjs:67-70, 77-82` |
| BitTorrent-трекеры                                 | `info_hash` = первые 20 символов SHA-1-топика, зашифрованные offer/answer                            | `torrent/dist/index.mjs:20-31`     |
| Nostr                                              | событие с `kind = 20000 + strToNum(topic) mod 10000` (эфемерный диапазон NIP-01) и тегом `x = topic` | `nostr/dist/index.mjs:44-48`       |
| «IPFS»                                             | на деле Waku (`@waku/sdk`, `createLightNode`): content topic `/trystero-<topic>/0/msg/json`          | `ipfs/dist/index.mjs:1-6`          |

Все Relay публичные, и подписаться на них может кто угодно. MQTT разрешает подписку по маске `#` (MQTT 3.1.1 §4.7.1.2). Публичные брокеры обычно её не запрещают, но на `broker.emqx.io` и `broker.hivemq.com` я это не проверял. Nostr-релей отдаёт события любому, кто подписался на нужные `kinds`. Поэтому оператор Relay, а часто и любой посторонний слушатель, собирает пары «топик + зашифрованный SDP».

### Шифрование SDP

`core/dist/crypto.mjs:12`:

```js
const genKey = async (secret, appId, roomId) => crypto.subtle.importKey("raw",
  await crypto.subtle.digest({ name: "SHA-256" }, encodeBytes(`${secret}:${appId}:${roomId}`)), …AES-GCM…);
```

Мы не передаём `password` (`trysteroAdapter.ts:53-61`), поэтому ключ равен `SHA-256(":call-ma:<roomId>")`. В README Trystero (раздел Encryption) прямо сказано:

> By default the SDP is encrypted using a key derived from your app ID and room ID to prevent plaintext session data from appearing in logs. This is fine for most use cases, however a relay strategy operator can reverse engineer the key using the room and app IDs.

Значит, шифрование защищает от случайного чтения логов, но не от того, кто знает ID. А ID восстанавливается по топику.

### Стоимость перебора

Задача: по наблюдаемому топику найти `id` из 36⁸, для которого `sha1("Trystero@call-ma@" + id)` даёт тот же топик. Соль — константа и одна на всех, так что одним проходом вскрываются сразу все комнаты, которые видел наблюдатель.

| Чем считаем                                                                   | Скорость SHA-1 | Полный перебор 36⁸ | В среднем (половина) |
| ----------------------------------------------------------------------------- | -------------- | ------------------ | -------------------- |
| Node `crypto.createHash`, 1 ядро (замер на этой машине)                       | ≈ 6,5·10⁵/с    | ≈ 50 дней          | ≈ 25 дней            |
| То же, 12 ядер                                                                | ≈ 8·10⁶/с      | ≈ 4 дня            | ≈ 2 дня              |
| Нативный код, CPU ~10⁸/с (оценка)                                             | 10⁸/с          | ≈ 8 ч              | ≈ 4 ч                |
| hashcat, одна RTX 4090, ~5·10¹⁰/с (порядок по публичным бенчмаркам, не замер) | 5·10¹⁰/с       | ≈ 1 мин            | ≈ 30 с               |
| Облачный GPU, ~1 $/ч                                                          | то же          | копейки            | —                    |

Без топика остаётся онлайн-перебор: подписываться на Relay под каждый кандидатный ID. Одновременно живых комнат единицы, поэтому шанс угадать на попытку — около N / 2,8·10¹², и при 1000 подписок в секунду полный перебор займёт около 90 лет. Так что угадать ID вслепую нереально. Реальная атака другая: подслушать топик на публичном Relay и снять с него хеш.

Итог: 41 бит против офлайн-атаки по SHA-1 ничего не стоят. Нужно либо около 128 бит секрета, либо секрет, который не попадает на Relay даже в виде хеша (см. §5).

## 3. Что будет, если в комнату войдёт третий

`TrysteroAdapter.join` (`src/connection/trysteroAdapter.ts:81-112`):

```ts
room.onPeerJoin = (peerId) => {
  room.addStream(localStream, { target: peerId });
  …
};
room.onPeerStream = (stream, peerId) => {
  if (connectedPeers.has(peerId)) return;
  connectedPeers.add(peerId);
  this._onStream?.(stream, peerId);
};
```

- Лимита на двух пиров нет. Каждому, кто вошёл, оба участника **сами отправляют** камеру и микрофон.
- Trystero строит полносвязную сеть: новый пир соединяется с каждым, кто уже в комнате.
- Если третий ничего не отправляет, `onPeerStream` для него не срабатывает и `remoteVideo` не меняется. В логе страницы появится только `Peer joined — connected!` (`src/app/controller.ts:86-88`), а его легко не заметить. Получается **незаметное прослушивание и подглядывание**.
- Если третий отправит поток, `showStream(els, 'remoteVideo', …)` (`controller.ts:83-85`) заменит картинку собеседника его потоком. Подмена видна, но звонок перехвачен.
- Вошедший раньше законного собеседника становится «собеседником» сам: никакой проверки, кто на том конце, нет.
- Пароль Trystero (`password`) включил бы ещё и challenge-handshake на `SHA-256(challenge:password:appId:roomId)` (`core/dist/handshake.mjs:5-31`). Пир без пароля не активируется. Но пароль защищает только от тех, у кого нет ссылки, если он едет в той же ссылке.

### Подмена собеседника (MITM)

- Сигнализация не аутентифицирована ничем, кроме знания ID. AES-GCM с ключом из ID защищает целостность только от тех, кто ID не знает. Relay, подобравший ID (§2), может читать, отбрасывать и подделывать offer/answer.
- Медиа идёт по DTLS-SRTP, а отпечаток DTLS-сертификата едет в SDP. Кто подделывает SDP, тот подставляет свой отпечаток и встаёт посередине. Пользователь ничем не может это проверить: UI не показывает ни отпечатков, ни кода сверки (SAS).
- Полный прозрачный MITM на Trystero сложнее простого входа третьим: участники ещё и находятся напрямую через другие Transport. Но для прослушивания он и не нужен, хватает §3.

## 4. Чем рискует ссылка Direct mode

`src/shared/sdp.ts`: `encodeSdp` = `JSON.stringify(desc)` → `deflate-raw` → base64url. **Это сжатие, не шифрование.**

Что внутри SDP и что получает перехвативший ссылку:

- **Пассивно** (прочитал ссылку или QR):
  - ICE-кандидаты, то есть локальные и публичные IP (host/srflx, при TURN — relay);
  - `ice-ufrag`/`ice-pwd`;
  - отпечаток DTLS;
  - набор кодеков и устройства.

  Расшифровать медиа нельзя: ключи SRTP выводятся из DTLS-рукопожатия на эфемерных ключах, а в SDP только отпечаток.

- **Активно, ссылка-offer.** Перехвативший может открыть её первым и сделать свой answer. Если звонящий вставит этот answer (`applyAnswerFromInput`, `src/app/directMode.ts:116-130`), звонок пойдёт к атакующему. Связи «этот answer — от того, кому я слал offer» нет: принимается любой валидный answer.
- **Активно, ссылка-answer.** Тот, кто может подменить ссылку в канале (например, взломанный мессенджер), подсовывает свой answer. Результат тот же.
- Третьего в Direct mode нет: одно `RTCPeerConnection`, один answer. Подслушать молча, как в комнате, нельзя, можно только занять место собеседника.
- Плюс Direct mode: не участвуют ни Relay, ни перебор. Риск сводится к доверию каналу, по которому передают ссылку.

## 5. Кандидаты в фиксы (для #49 / решения по карте)

Только клиент, без своей инфраструктуры:

1. `crypto.getRandomValues` вместо `Math.random()`.
2. **Секрет комнаты отдельно от топика.** В фрагменте ссылки два поля: короткий ID (уходит в топик) и длинный пароль, ≥128 бит, передаётся в `joinRoom({ appId, password })`. Relay видит только хеш ID, а ключ AES и handshake зависят от пароля, которого на Relay нет совсем. Перебор топика перестаёт что-либо давать.
3. **Два пира максимум.** После первого `onPeerStream` не отправлять поток новым пирам, игнорировать их и, возможно, выйти из комнаты (`room.leave()`), чтобы ссылка перестала работать.
4. Заметное предупреждение в UI при входе третьего вместо строки в логе.
5. Сверка собеседника: короткий код из отпечатков DTLS обеих сторон (SAS), который люди сравнивают голосом. Открытый вопрос карты: нужно ли это бабушке.
6. Direct mode: шифровать SDP в ссылке ключом, который передаётся отдельным каналом, или явно предупреждать, что ссылку нельзя пересылать через ненадёжный канал.

## Не проверено

- Разрешают ли конкретные публичные MQTT-брокеры по умолчанию подписку на `#` (по спецификации MQTT маска допустима).
- Скорость SHA-1 на GPU взята как порядок величины из публичных бенчмарков hashcat, не замерена. Замер только Node на CPU.
